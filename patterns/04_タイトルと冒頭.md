# タイトルと冒頭

**測った34本のうち、冒頭で読者を名指ししているのは4本だけ。**
残り30本は**読者を呼ばずに、症状・矛盾・損失で囲い込んでいる。**

---

## 1. 読者の置き方：5つのやり方

| やり方 | 実例 | 人 |
|---|---|---|
| **症状で囲い込む** | 「Claude Codeを使っている人ならみんな感じてると思いますが」 | sesere |
| **自分の混乱を差し出す** | 「「typeよりinterfaceを使うように！」というブログをよく見ましたが、業務の時は全部typeで型を定義してました。」 | luvmini511 |
| **損失から始める** | 「設計をないがしろにすると、低凝集密結合な構造に陥り、変更容易性が低下してしまいます。」 | MinoDriven |
| **思い込みを疑問形で突く** | 「Claude Code、まだ「コードを書くツール」だと思ってませんか？」 | minorun365 |
| **名指しする** | 「この記事は Claude Code を初めて試そうとされている方向けの記事です。」 | morizyun（2本）、KNR109（2本） |

### 名指しは4/34本しかない

| 窓 | 読者を名指し | ゴールを宣言 |
|---|---|---|
| 冒頭600字 | **4本**（morizyun 2本・KNR109 2本） | 14本 |
| 冒頭1,500字 | 5本（＋Sicut_study Docker編・640字目） | 18本 |
| 本文全体 | **6本** | 21本 |

**「読者を名指しするのは少数派」は、窓を本文全体まで広げても変わらない（6/34本）。**

**ゴール宣言のほうは窓しだいで14本にも21本にもなる。**
「半分弱」と読むのは冒頭600字に限った話で、**最後まで読めば6割は何らかの宣言をしている。**
この数字を根拠に「ゴールは書かなくていい」とは言えない。

ただし**名指しにも利点がある。** morizyun は1文目に固定することで、
**同じ型でツール名だけ差し替えて2本目を書けている。** 連載にするなら名指しが効く。

### ひろほの場合

現状のブログ冒頭は「「先月の数字は？」と上司に聞かれるたびに、〜していませんか。」
**＝症状で囲い込む型。多数派と一致している。** 変えなくていい。

**足すなら、morizyun 型の「連載のための名指し」を2文目に。**

```
「先月の数字は？」と上司に聞かれるたびに、…していませんか。   ← 症状（現状のまま）
この記事は、Claude Codeを初めてGA4につなぐ人向けです。      ← 名指し（連載の枠を作る）
```

## 2. リードの長さと役割

| 人 | リード | 占有率 | 役割 |
|---|---|---|---|
| sesere | 挨拶1行 | — | **記事の目的を書かない。** 経験2週間と自己申告して権威を下げる |
| catnose99（Nani） | 205字・3文 | **3.3%** | 何を作ったか＋この記事は何の話か。**効能を書かない** |
| luvmini511 | 107字・3文 | 5% | **矛盾の提示**（答えの予告ではない） |
| morizyun | 3行 | — | 読者指定＋公式URL |
| uhyo | 474字 | 5% | **340字が前提と免責。賞味期限まで先に書く** |
| catnose99（RSS） | 515字 | 23.1% | 他人の記事の課題整理（**名前が知られていないとき**） |
| c60evaporator | 長い | — | 既存教材の欠落＋埋める範囲＋章立て予告＋保険の4点 |

**2,000字なら、リードは100〜200字（5〜10%）。**

### リードでやってはいけないこと

| ❌ | 誰がそうしていないか |
|---|---|
| 効能を並べる | catnose99 は宣伝を3.3%に閉じ込めている |
| 答えを予告する | luvmini511 は矛盾だけ置いて答えを言わない |
| 「この記事では〜を紹介します」で終わる | 34本中20本はゴール宣言すらしていない |
| 前提を本文に混ぜる | uhyo はリードで外部リンクに逃がしている |

### ひろほのリードに入れる3つ（uhyo 型）

```
① この記事が前提にしていること
② いつ時点の話か（日付・バージョン）
③ そのうち変わる可能性
```

**Claude Code は更新が速いので、③を書いておくと記事が古くなっても嘘にならない。**

## 3. タイトル：型で評価は変わらない。決め手は別にある

> **訂正（2026-09-20）**
> 最初の版に「型ごとのLGTM中央値」の表を置き、「してみた」を✕、
> 「完全版」「まとめ」などを◎と判定していた。
> **これはQiitaのLGTMとZennのいいねを足した人為物で、間違いだった。取り下げる。**
> プラットフォームを分けて信頼区間をつけ直した表は `method/01` の1章。
> 検算は `python3 tools/robust.py`。

### 分けて測り直した結果

| | 差があると言える型 | 判定できなかった型 |
|---|---|---|
| Qiita（n=1,000） | 高い：なぜ〜のか（n=12）／低い：入門・はじめて・初心者（n=75） | 残り11の型すべて |
| Zenn（n=1,920） | 高い：「まとめ」「集」で終わる（n=20）／低い：数字＋選・個・つ（n=67） | 残り11の型すべて |

**13の型のうち、はっきり差が出たのは各サイト2つだけ。しかも2サイトで一致していない。**
**「タイトルの型を変えれば読まれる」とは、この標本からは言えない。**

### それでも「してみた」は使わない

理由は評価の数字ではなく、**検索とのつながり**。

**書き手の行動が主語で、読み手の得るものがタイトルに入っていない。**

| ❌ 書き手が主語 | ⭕️ 読み手の得るものが主語 |
|---|---|
| Claude CodeとGA4を連携してみた | Claude CodeとGA4の連携｜5つの手順で全データを読ませる方法 |
| MCPサーバを作ってみた | コマンド一発でMCPサーバを設定する |

Qiita・Zennは一覧とトレンドから読まれるので、タイトルは**目を引けばよい**。
**自社サイトのブログは検索から来るので、タイトルが検索語と一致しないと始まらない。**
「してみた」はどの検索語とも一致しない。

**ひろほのブログがQiita・Zennと違う土俵にいる、というのがここでの結論。**
型の当たり外れを真似するのではなく、**4章の5つのレシピ（作り方）を真似する。**

### 長さ

- 中央 **33字**／25〜75%の帯 **25〜43字**
- 50字を超えると一覧で切れる。25字を割ると検索語が入りきらない

## 4. タイトルの作り方：5つのレシピ

### ① 症状の鍵カッコ＋断定を外す語尾（sesere）

```
Claude Codeの「すぐルール忘れる問題」を解決する超効果的な方法を見つけた気がする
└ 読者のセリフ            └ 解決する      └ 断定を外す
```

**「見つけた気がする」で断定を外すと、「本当かよ」と開きたくなる。外れても誰も怒らない。**

### ② 誰が・いつ・何をしたら・どうなったか（kojimadev）

```
30代後半になって初めて発信活動を始めたら人生が変わった話
└ いつ        └ 何を        └ どうなった
```

**タイトルだけで、自分が対象かどうか判定できる。**

### ③ 読者の状態＋網羅の宣言（Sicut_study）

```
Dockerがわからない人へ。これ1本で0から学べる丁寧なDocker入門
└ 読者の状態     └ 網羅     └ 丁寧さ
```

### ④ ツール名＋成果物名で、差し替えられる形（morizyun）

```
〈ツール名〉 を初めて使う人向けの実践ガイド
```

**ベネフィットも数字も入れないので、ツール名を替えるだけで連載になる。**

### ⑤ 違いだけで終わらせない（luvmini511）

```
interfaceとtypeの違い、そして何を使うべきかについて
└ 違い          └ 何を使うべきか（＝本文の字数43%）
```

**タイトルの後半と、本文の字数配分が一致している。**
