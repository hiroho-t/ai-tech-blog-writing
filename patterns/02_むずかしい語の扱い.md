# むずかしい語の扱い

**なぜ分かりやすいのか。** 12人の初出処理を並べると、6通りに分かれた。
そして**同じ人が記事の中で2通りを使い分けている。**

※ この6通りは、34本を読んで分けたもの。**機械で数えた分類ではない。**
別の記事を足せば7通り目が出るかもしれない。

---

## 6つの型

| # | 型 | 実例（短い引用） | やっている人 |
|---|---|---|---|
| 1 | **述語 → 名前** | 「グローバルIPアドレスとプライベートIPアドレスを変換する機構を、NAT (Network Address Translation)と呼びます。」 | c60evaporator、luvmini511 |
| 2 | **名前＋役目を1行** | 「Turso: SQLiteでユーザーの設定などを保存」 | catnose99、morizyun |
| 3 | **既知の語1つに引き寄せる** | 「awaitのようにPromiseから中身を取り出すのがuseの役目ということです。」 | uhyo、sesere |
| 4 | **難しい定義を出してから書き換える** | 「まずはよくあるDokerの説明から行います(知らない方は難しいやつです)」→ 定義 → ゲーム機のたとえ | Sicut_study |
| 5 | **括弧で1語だけ足す** | 「インセプションデッキ(メンバーみんなで議論して決めた共通認識)」 | kojimadev、minorun365 |
| 6 | **連鎖的に定義する** | 「技術的負債とは〜」→「変更容易性」を定義 →「理想的な構造」を定義 | MinoDriven |

## 型1「述語 → 名前」が一番移しやすい

**用語名を文の後半に置く。** 読者が知らない略語を文頭で浴びずに済む。

ひろほがすでに書いている文をこの語順にすると、こうなる。

| | 文 |
|---|---|
| 現状 | Googleで何番目に出ているかを確かめる仕組み（Googleサーチコンソール）に追加する |
| 型1 | **Googleで何番目に出ているかを確かめる仕組みを、Googleサーチコンソールと呼びます。** これに追加します |

どちらも成立する。**ただし、その語がその記事の主役かどうかで決める。**

| 主役かどうか | 使う型 | 理由 |
|---|---|---|
| 主役（記事で何度も出る） | **型1**（1文かけて定義する） | 以降ずっと使うので、一度きちんと置く |
| 脇役（1〜2回しか出ない） | **型5**（括弧で1語） | 文を止めない |

**1本の記事で型1を使うのは2〜3語まで。** それ以上やると定義文が続いて読めなくなる。

## 比喩の位置は2通りある。これが分かれ目

同じ「丁寧に教える型」の2人で、**比喩の位置が真逆。**

| | 比喩の位置 | 書き方 |
|---|---|---|
| **Sicut_study** | **説明の主軸**（比喩が説明そのもの） | 公開鍵と秘密鍵＝シンデレラのガラスの靴。以降「ガラスの靴(公開鍵)」と二重表記で通す |
| **c60evaporator** | **正確な定義の後ろの補助** | 定義を1文で言い切った直後に「〜とみなすと、理解しやすいかと思います」で見立てを足す |

### どちらを選ぶか

| 読者 | 選ぶ位置 |
|---|---|
| その用語を**使う側**（設定する・操作する） | **主軸**（Sicut_study 型）。正確さより手が動くことが大事 |
| その用語を**判断する側**（選ぶ・説明する） | **補助**（c60evaporator 型）。あとで他人に説明するので定義が要る |

ひろほの読者は①兼務でホームページを任された担当者 ②Webディレクター。
**①は使う側、②は判断する側。** だから**両方要る。**

順番はこう。

```
1. 述語 → 名前 で定義を1文（②のため）
2. 「〜とみなすと分かりやすいと思います」で見立てを1文（①のため）
3. 以降は正式名だけで通す
```

## 比喩には終わらせ方がある

**比喩を張ったままにしない。必ず現物に戻す。** これを守っているのが MinoDriven と minorun365。

### MinoDriven の5手（モジュール分割 → キャビネット）

| 手 | やること |
|---|---|
| 1 | 置き換える対象を**1つに絞る** |
| 2 | **先に「整っている状態」を見せる** |
| 3 | **次に「散らかった状態」を見せ、痛みを具体物に変換する**（「バグ」→「手を切る」） |
| 4 | **そこで初めて現物に接続する**（「システムの内部構造は、今このように散らかった状態なのです。」） |
| 5 | **たとえの語彙だけで用語を再定義して閉じる**（「上手く整理できるように構造を考えるのが設計です。」） |

### minorun365 の2手

たとえを置いたら、**その場で意味を3つに分解する。**

```
「優秀な中途入社の後輩がフルリモートで4人くらい一気にチームに入ってきた、という感じです。」
↓ すぐに
・業務の背景を説明すれば自分で考えて動いてくれる
・わからないことは質問してくる
・複数の仕事を同時に任せられる
```

### ただし「比喩で止める」人もいる

> **訂正（2026-09-20）**
> 最初の版に「『〜みたいなもの』で止めているのは1人もいない」と書いたが、**間違いだった。**
> 34本を全文検索すると、比喩で止めている文が複数ある。

> コンテナはいわば小さなPCのようなもので、そのPCにはすでにDBに必要なものがすべて含まれています。
> —— [Sicut_study／Docker入門](https://qiita.com/Sicut_study/items/4f301d000ecee98e78c9)

erukiti も「これをタスクのテンプレートみたいなものにします。」と書いて、そこで止めている。

**止めても成立するのは、直後にコマンドの出力や画面が根拠を補うとき。**
Sicut_study は比喩の直後に `docker run` の結果を貼るので、読者は比喩が合っているか自分で確かめられる。

**ひろほは言葉だけなので、確かめる手段が読者にない。だから現物に戻す1文が要る。**
「移せる／移せない」の線は、ここでも**コードと図があるかどうか**で引かれる。

## やってはいけない4つ

| ❌ | なぜだめか | どう直すか |
|---|---|---|
| 比喩を出して次の話に行く | 読者は比喩だけ覚えて、用語を覚えない。**コードや画面で確かめられる記事なら止めてよいが、言葉だけの記事では戻す** | 現物に戻す1文を足す（MinoDriven の4手目） |
| 定義文の中に未定義の語を入れる | 定義が増殖する | その語もその場で定義する（MinoDriven の連鎖）か、その語を使わない言い方にする |
| 難しい定義を隠して、易しい説明だけ書く | 読者があとで公式ドキュメントを読んだとき対応が取れない | **「これは難しいやつです」とラベルを貼って併記する**（Sicut_study） |
| 「〜とは」で始めて長い定義を書く | 述語が最後に来て、読み終わるまで意味が分からない | **述語 → 名前**の語順にする（型1） |

## 「かと思います」で読者の理解状態を代弁する

c60evaporator が VPC 8回・パラメータ 23回使っている。

> 既にご存知の内容も多いかと思いますが、VPCを理解するためにはネットワークの知識が必要となるため、簡単に解説します。

**基礎を説明する前の断り。上から教える口調を避けるための装置。**

ひろほのブログは「読者を見下さない」のが前提なので、これは直接使える。

| 場面 | 言い方 |
|---|---|
| 基礎から説明するとき | 「ご存じの方には当たり前の話かもしれませんが、」 |
| 読者が知らないと決めつけたくないとき | 「ここは、もう済んでいる方は飛ばしてください。」 |
| 自分の読みを出すとき | 「〜と考えられます」（事実と分ける → `writers/11`） |
