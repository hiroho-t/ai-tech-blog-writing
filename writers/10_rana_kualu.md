# rana_kualu（Qiita・9本ヒット・中央LGTM 724）

> 種類：**言葉で伝える型**。**見出し68本・1見出しあたり138字**という、測った34本で最も細かく刻んだ記事の持ち主。

**一行でいうと**：
他人の一次資料を訳し、そこに**「読者コメントの翻訳」と「自分の一言」を後付けする三層**で、
見出しだけ読んでも通じる状態まで刻む人。

---

## 型は記事構成ではなく「枠」

この人の本当の型は、記事ごとの構成ではなく**毎回同じ5枠**。

| 枠 | 中身 |
|---|---|
| ① 訳者まえがき | なぜ読む価値があるか（見出しなし） |
| ② 訳文 | 他人の本文。**見出しは原文の英語のまま残す** |
| ③ **コメント欄** | **原文サイトの読者コメントの翻訳** |
| ④ **感想** | 自分の立場。**自分が採る1〜2点だけ名指しする** |
| ⑤ その他 | 関連リンク |

**③と④が、測った12人でこの人だけがやっていること。**

## 読者の置き方

**読者を名指しせず、「あなた」を登場人物にして物語の中に引き込む。**

「コピペをやめろ」では訳文の中で私＝攻撃者、あなた＝マージする側として役を振る。

> あなたはそれをマージしました。

## むずかしい語の初出処理

**英語見出しを訳さず残し、その直下に日本語1行で言い直す。これが実質の言い換え装置。**

```
What happens next?
それでなにが起こる？

1.Coding is about problem-solving.
コーディングは、問題解決の手段である。
```

用語そのものの定義は薄い。代わりに**訳注を本文に割り込ませる。**

> ※訳注：実際はコピペしてもLRIがありません。
> —— コピペをやめろ

## 「読み飛ばし前提のレイアウト」が成立する4つの条件

「65のこと」は見出し68本・呼びかけ56回。この型が崩れずに1,127 LGTMまで行っている条件。
**1つでも欠けると成立しない。**

### ① 項目が互いに参照しない

項目37を読まずに38を読んでも欠けが出ない。
支えているのが**H3ゼロ・箇条書きゼロ・太字ゼロ**。
**入れ子も強調もなく、見出しが唯一の階層。** だからどこから入ってもよい。

### ② 見出しが主張の全文になっている

「The golden rule is planning.」／「最優先すべきは計画である。」
**体言止めの名詞句ではなく、言い切りの1文。**
だから目次だけ読んでも要約として成立する。

### ③ 文が短い

平均32.0字・80字超え1%。1項目3文なので、**読むと決めた人が10秒で終わる。**
長文が混ざると刻んだ意味が消える。

### ④ 書き手が「全部読まなくていい」と明言する

> 気になった幾つかをピックアップして心にとどめるとよいでしょう。
> —— [コーディングを始めたときに知っておきたかった65のこと](https://qiita.com/rana_kualu/items/63ad0f68d66c5f0a464b)

さらに**自分が採るのは64番と65番だと名指しする。**

**読み方の許可を書き手が先に出しているから、読み飛ばしが手抜きにならない。**

## ひろほの2,000字で使うとH2は何本が上限か

| 計算 | 結果 |
|---|---|
| 実測密度 138字／見出し1本 → 2,000 ÷ 138 | **14本** |
| 項目本文だけ（中央値91字）→ リード・まとめ・FAQで600字使うとして (2,000 − 600) ÷ 91 | **15本** |
| **上限** | **14本。安全側は12本** |
| 1本あたり | 見出し＋本文140字以内・3文以内 |

### ただし、ひろほの条件と2つ衝突する

**① 実数が1文を食う。**
「2026年8月27日に、1時間かからずにつないだ」で38字。
3文のうち1文が実数に取られるので、**実数を置く項目は実質2文になる。
実数を置くのは14本のうち3〜4本に絞る。**

**② ひろほの構成は順番依存。**
「課題 → 思い込み → 手順 → つまずき → 実例 → まとめ → FAQ」で、
思い込みは課題を読んでいないと効かない。

**刻む型は記事全体には使えない。1ブロックの中だけに使う**
（例：手順を8本、つまずきを5本に刻む）。

## 再現性の担保

| 項目 | ある／ない | どう書いているか |
|---|---|---|
| 環境・バージョン・日付 | **弱い**（`env` 1／2） | 「2021/11にVSCode本体に入った機能」とインストールコマンドの版数だけ |
| 手順の粒度 | ある | 規範を3文（MUST／SHOULD／SHOULD）＋インストールコマンド1行。65のことは1項目＝1つの態度 |
| 成功判定 | **ある**（コピペをやめろのみ） | 「スキャンが完了すると、疑わしい制御文字が含まれているファイルを教えてくれます。」＋確認画面 |
| つまずき・失敗 | **自分のではなく読者のつまずきを転載する** | コメント欄に「コードサンプルが動かなかった」を訳して置く。さらに感想では**自分の誤りを取り消し線で残して訂正する** |
| 前提の棚卸し | **ある** | 2本とも第1行で「これは翻訳である／原文はこれ」を宣言し、原論文のURLまで置く。**出典の棚卸しを冒頭で完了させる** |

```
StackOverflowからのコピペをやめろ。今すぐにだ。
コーディングを始めたときに知っておきたかった65のこと

```

母集団では「命令形」型のLGTM中央値は447で、全体の125の3.6倍（→ `method/01`）。

| 文 | 役割 |
|---|---|
| 1 | 既知の身近な例（「その昔コピペできない文章というものがありました。」） |
| 2 | 一次資料の存在 |
| 3 | **一次資料は読みにくいと言い切る** |
| 4 | だから噛み砕く |

## ひろほのブログに移せるもの

1. **一次資料（公式ドキュメント・リリースノート）のURLを冒頭3文以内に出し、
   「原文は長い／英語だけ」と言い切ってから自分の要約に入る**
2. **見出しを体言止めではなく言い切りの1文にし、直下に同じ内容を1行で言い直して、
   見出しだけ読んで通じる状態にする**
3. **記事末に「私が実際に使っているのはこれ」の見出しを1本置き、
   本文で挙げたもののうち自分が採る1〜2個だけを名指しする**

## 移せないもの

1. **見出しを68本に刻む型そのまま。**
   2,000字では上限14本で、1項目（本文91字・3文）は
   「日付・回数・金額の実数を必ず入れる」条件と両立しない
2. **「コメント欄」＝海外記事の読者コメントの翻訳。**
   **原文が他人の記事だから成立する装置**で、自分のオリジナル記事には置けない。
   置くならFAQか、自分の案件で実際に出た質問に置き換える
