# MinoDriven（Qiita・4本ヒット・中央LGTM 762）

> 種類：**言葉で伝える型**。3本すべてコードブロック**0〜1本**。
> しかも「技術記事の書き方」という**方法論の記事を自分で書いている**ので、宣言と実行を突き合わせられる。

**一行でいうと**：
特許明細書の順番（課題 → 原因 → 解決技術 → 効果 → 留意点）を毎回同じ型として使い、
**専門用語は「定義1文 → 日常のたとえ → 現場での現れ方」の3段でほどく**人。

---

## 本人が宣言している型と、実際に守れているか

「伝えたい人に届ける技術記事の書き方」で、本人はこの基本構成を宣言している。

```
タイトル／概要／この記事で伝えたいこと／解決したい課題／課題の原因／
課題を解決する技術（概要・効果・どう解決されるか・応用事例のカタログ化）／留意点・デメリット
```

他2本と突き合わせた結果。

| 宣言した要素 | 非エンジニアに説明 | 認知バイアス |
|---|---|---|
| 概要 | ○「これはなに？」 | ○「これはなに？」 |
| この記事で伝えたいこと | ○「この記事のゴール」2点 | ○「この記事のゴール」3点 |
| 解決したい課題 | ◎ 独立見出し「状況と課題の整理」に30行超 | △ 独立見出しなし。「これはなに？」に圧縮 |
| 課題の原因 | △ 独立見出しなし | ○「認知バイアスとは」が原因の説明 |
| 課題を解決する技術 | ○「伝え方」以下 | ◎ 6例すべてに「どうすればよいか」を対で置く |
| 技術の効果 | △ 「分かりやすい」の1文のみ | △ 明示なし |
| 応用事例のカタログ化 | △ 比喩を1件追加（2件でカタログとは言い難い） | ◎ 6例の並列がカタログそのもの |
| **留意点・デメリット** | **✕ ない** | **✕ ない** |

### 守れていないところが3つある

**① 留意点・デメリットが2本ともゼロ。**
本人は「あらゆることを解決する、デメリットのない万能な技術は存在しません。」と書いているのに、
たとえが通じない相手やたとえが誤解を生むケースを一切書いていない。

**方法論を語る記事では自分のルールを守り、実務記事では守っていない。**

**② 宣言したタイトル型を3本とも使っていない。**
本人は「僕の記事はほとんどが「（解決技術）で（課題）を爆殺する」のフォーマット」と書いているが、
この3本はどれもそうなっていない。

**③ 「解決したい課題」を独立見出しにするルールが、認知バイアスで崩れている。**
課題は概要の2文に圧縮され、代わりに原因（「認知バイアスとは」）が先に来る。
**LGTMは762でこの3本中最多なので、崩しても読まれている。**

> **ここから分かること**：型は守ると安定するが、型を崩した記事が一番読まれることもある。
> 型は「毎回ここまでは落とさない」の下限として使う。

## 読者の置き方

**冒頭で読者を名指ししない。3本とも第1文は読者ではなく「損失」から始まる。**

> ソフトウェア開発において、設計をないがしろにすると、低凝集密結合な構造に陥り、変更容易性が低下してしまいます。

読者指定は「概要」の最後の1文に置く。

## 記事の骨格

**3本すべて、最初の2本の見出しが同じ。**

```
1. これはなに？（／なにこれ？）
2. この記事のゴール
--- 以下、記事ごと ---

【非エンジニアに説明】見出し9本
3. 状況と課題の整理
4. 伝え方
5. まず設計が解決する課題やメリットを伝える
6. なぜ設計が必要なのか
7. ユビキタス言語の策定活動に繋げる
8. 【余談1】…
9. 【余談2】…

【認知バイアス】見出し12本
3. 認知バイアスとは
4. 設計を歪める認知バイアスの例
5〜10. ◆アンカリング効果／◆多義の誤謬／◆早まった一般化／◆レッテル貼り／◆現状維持バイアス／◆分析麻痺症候群
11. まとめ ／ 12. 参考文献
```

**中身が何であれ入口の2枚は同じ。**
そして本題は「課題 → 原因 → 解決」の順で、**解決策の側から始めることが一度もない。**

## 1文・1段落の作り方

| 指標 | 技術記事の書き方 | 非エンジニアに説明 | 認知バイアス |
|---|---|---|---|
| 本文字数 | 5,626字 | 5,861字 | 5,694字 |
| 1文の平均 | 31.5字 | 46.0字 | 35.6字 |
| 80字超え | 1% | 8% | 2% |
| 1見出しあたり | **268字** | 651字 | 474字 |

1文ずつ改行して積む。

段落の役割は**「たとえを出す」ではなく「たとえから1つだけ教訓を抜いて、次の段落に渡す」。**
だから**たとえが2段落にまたがらない。**

通販番組の値引きでアンカリング効果を3文で説明したあと、こう閉じる。

> この販売価格の例では、そもそも最初に提示された価格が妥当かどうかを検証する必要があります。
> —— 認知バイアス

## むずかしい語の初出処理

### ① 定義を独立した見出しに切る

認知バイアスは見出し3を丸ごと定義に使う。
「先入観や思い込み、偏見や誤解などによって非合理的な判断をしてしまう心理現象です。」
と書いたうえで、すぐ日常例（災害時に周りが逃げる方向につられる）を置く。

### ② 定義文に出た用語を、その場で連鎖的に定義する

「技術的負債とは、開発速度を貶める粗悪な構造のことを指します。」
→ その中の「変更容易性」をすぐ次の文で定義
→ さらに「理想的な構造」を定義。**3段つなぐ。**

**用語を放置したまま次の話に行かない。**

## たとえ話の作り方（ひろほの読者層と完全に一致する記事から）

### 実例1：モジュール／クラス分割 → キャビネット。運びは5手

| 手 | やること |
|---|---|
| 1 | 置き換える対象を1つに絞る（モジュール・クラス → 収納） |
| 2 | **先に「整っている状態」を見せる** |
| 3 | **次に「散らかった状態」を見せ、痛みを具体物に変換する** |
| 4 | **そこで初めて現物に接続する** |
| 5 | **たとえの語彙だけで用語を再定義して閉じる** |

2の実例。

> 本、文房具、オモチャ……それぞれの収納場所が決められていて、整理して正しく収納されていれば、例えばオモチャを取り出したいといった場合にすぐに取り出せますね。
> —— [非エンジニアサイドに技術的負債や設計を説明するノウハウ](https://qiita.com/MinoDriven/items/2d63dcaa92b50b049889)

3では「ハサミが紛れ込んでいたら探す最中に手を切るかもしれない」と書く。
**「バグ」を「手を切る」に翻訳している。抽象語を痛みの身体感覚に落とす一手。**

4で「システムの内部構造は、今このように散らかった状態なのです。」
5で「上手く整理できるように構造を考えるのが設計です。」

### 実例2：ユビキタス言語 → 「おどうぐばこ」1つ vs 種類別の引き出し。4手

| 手 | やること |
|---|---|
| 1 | 極端に悪い例を1つだけ出す（「おどうぐばこ」と書かれた箱がたった1つ） |
| 2 | **断定せず、読者に問いを投げて自分で結論させる** |
| 3 | **たとえを張ったままにせず、対応表を1文で明かす** |
| 4 | 読者の業務語彙で例を列挙する |

2の実例。

> このたったひとつの箱だけで、様々な種類の道具を上手く整理して収納できるでしょうか？
> —— 同記事

4では商品／注文／在庫／予約／配送を並べ、
そのうえで「発注金額」が顧客側の発注か仕入れ側の発注かで意味が違う、と読者の実務の言葉で矛盾を見せる。

## この人の一番の武器

**読者が次に口に出す文そのものを書いて渡すこと。**

「説明のコツ」ではなく**「説明の台詞」を引用ブロックで丸ごと渡す。**

> 非エンジニアサイドに説明する内容は下記のように引用で表現しますので、注意して読み進めて下さい。
> —— 同記事

こう宣言してから、**引用56行を台本として渡す。**

```
地の文   ＝ エンジニア向けの解説（なぜその言い方にするか）
引用ブロック ＝ 非エンジニアに実際に言う台詞
```

**この2層構造をやっているのは、測った12人でこの人だけ。**

## 再現性の担保

| 項目 | ある／ない | どう書いているか |
|---|---|---|
| 環境・バージョン・日付 | **ほぼない**（`env` 1／0／0） | 唯一が「2021/11/23時点の実績」 |
| 手順の粒度 | ある | 「構成1〜7」の7段で、1段が1〜3文。**1手順＝1判断で、作業ではない** |
| 成功判定 | **ない** | 「いつも「分かりやすい」と反応をいただいております」が唯一で、定性のみ |
| つまずき・失敗 | **ほぼない**（`pitfall` 1／0／3） | **自分が失敗した話を一度も書いていない** |
| 前提の棚卸し | **ある** | 3本すべてに「この記事のゴール」見出しを置き、箇条書き2〜3点で読者が得るものを先に確定させる |

## タイトルと冒頭の型

**「（動詞つきの連体修飾）＋（名詞）」。必ず動詞を1つ入れる。**

```
設計を歪める認知バイアス
└ 動詞  └ 名詞
非エンジニアサイドに技術的負債や設計を説明するノウハウ
```

リード文の役割は**「損失の提示」1本。**
損失の1文から始め、次の2文で「設計スキルを高めれば解決するはずなのに、
認知バイアスで判断を誤る」と**読者の思い込みを折る。**

## ひろほのブログに移せるもの

1. **兼務担当者に実際に言う台詞を引用ブロックで丸ごと書き、
   地の文は「なぜその言い方にするか」の解説に回して2層にする。**
   コードブロックが使えない代わりに、**引用ブロックを成果物の置き場にできる**
2. **1つの見出しの中を「用語の定義1文 → 日常のたとえ → Claude Codeでの現れ方 → どうすればよいか」の4段で回し、
   同じ形を記事内で繰り返す。**
   たとえは「良い状態 → 悪い状態 → 具体的な痛み」の3文で閉じる
3. **「この記事のゴール」見出しを箇条書き2〜3点で冒頭に置き、読者が得るものを先に確定させる**

## 移せないもの

1. **留意点・デメリットを書かない省略。**
   本人が必要と宣言しながら実務記事2本でゼロなので、手本にならない。
   **2,000字のひろほは、逆にここを1段落（150字程度）確保したほうがいい**
2. **たとえ話に画像5枚を添える運び。**
   写真なしなので、たとえを言葉だけで閉じる必要がある。
   ただし**実例1の引用文は画像なしでも成立しているので、文の運び自体は移せる**
