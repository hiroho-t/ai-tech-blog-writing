# Sicut_study（Qiita・32本ヒット・中央LGTM 509）

> 種類：**丁寧に教える型**。プールに32本入っている、測った中で最多のヒット数。

**一行でいうと**：
読者を「いま道具を目の前にしている人」の位置に立たせ、**わざと一度つまずかせてから直すところまで**を全部見せて、身体で覚えさせる人。

---

## 読者の置き方

**2本とも、読者の指定を冒頭直後に置く。**
Docker編は見出し「対象読者」で箇条書き5行。最後の1行が「難しい説明で挫折した人」。
**挫折経験そのものを読者条件にしている。**

本文では二人称に切り替える。「あなた」（Docker 3回／Git 2回）、「みなさん」（Docker 5回）。
読者を場面の中に立たせる言い方をする（「いまあなたの目の前にはゲーム機があります」）。

命令形は使わない。「〜しましょう」が Docker 11回・Git 23回。「してください」はそれぞれ1回だけ。
**誘うが、命じない。**

---

## 記事の骨格

見出しに `##` ではなく `#` を使う。

```
【Docker入門】見出し12本・1見出しあたり680字
はじめに／対象読者／目次
1. Dockerとは何か？なぜ使うのか？
2. Dockerを導入してみよう
3. コンテナを起動してみる
4. Dockerfileでイメージを作ろう
5. APIをイメージで起動する
6. Docker Composeで楽に起動しよう
感想をお待ちしております！／おわりに／メンバー募集

【Git図解】見出し19本・1見出しあたり498字
はじめに／動画で学びたい方へ／おすすめ記事
1. Gitとは？ ／ 3. GitHubとは？ ／ 2. Gitのインストール ／ 3. Gitの初期設定
4. リポジトリを作ろう ／ 5. Gitワークフロー ／ 6. コミットは細かくする
7. ステージングの変更を消す ／ 8. 特定のファイルをgitの管理外にする
9. 履歴を確認する ／ 10. コンフリクトの解消 ／ 11. ブランチを作ってプルリクを作ろう
12. コミットをなかったことにする ／ 13. マージとリベース ／ おわりに
```

### 型：見出しに連番を振り、動詞で終える

「〜してみよう」「〜を作ろう」「〜を消す」。
**連番があるので途中から読めない。上から順に手を動かす前提が、見出しだけで伝わる。**

Git編は番号が「1 → 3 → 2 → 3」と崩れている箇所があるのに読者が迷わない。
**各見出しが動作名になっているから、番号ではなく動作で位置が分かる。**

前半（1〜5）で概念と最小の1周を終える。
後半（6〜13）は「本番で困ること」だけを1つ1見出しで並べる。

| 指標 | Docker入門 | Git図解 |

| 本文字数 | 8,166字 | 9,953字 |
| 1文の平均 | 44.8字 | **33.1字** |
| 80字超え | 7% | **1%** |
| 箇条書き | 14個 | **0個** |
| 図 | 5枚 | **58枚** |

> コンテナはいわば小さなPCのようなもので、そのPCにはすでにDBに必要なものがすべて含まれています。

Git編は箇条書きが0個。**箇条書きの代わりに図を置いている。**

## むずかしい語の初出処理

### ① 難しい定義を先に出して、「これは難しい」とラベルを貼ってから書き換える

> まずはよくあるDokerの説明から行います(知らない方は難しいやつです)
> —— 同記事

こう予告してから公式風の定義を引用ブロックで出し、
**その直後に、同じ内容をSwitchとゲームソフトで言い直した引用ブロックを並べる。**

定義を隠さないのがポイント。
「これは難しい」とラベルが貼ってあるので、**読者が自分の理解力を疑わずに済む。**

### ② 身近な物語に役を割り当てて、以降は二重表記で通す

> 公開鍵と秘密鍵はシンデレラのガラスの靴のような関係があります。
> —— [【図解解説】これ1本でGitをマスターできるチュートリアル！【完全版】](https://qiita.com/Sicut_study/items/0318cc136c189b179b7f)

以降は「ガラスの靴(公開鍵)」と括弧で正式名を併記し続ける。
**比喩に乗り換えたままにせず、用語と二重表記でつなぐ。**

## 再現性の担保

| 項目 | ある／ない | どう書いているか |
|---|---|---|
| 環境・バージョン・日付 | **ある。ただしコードブロックの中だけ** | `docker -v` の出力として `Docker version 23.0.1` を貼る。**「コマンドを打つ→出力を貼る」形で、本文には書かない** |
| 手順の粒度 | **1手順＝1コマンド** | `docker pull` と `docker run` を別のブロックに分け、間に説明を挟む。オプションが増えたら**1つずつ箇条書きで訳す**（「--name : コンテナにpostgresと名前をつけました」） |
| 成功判定 | **ある。ほぼ全手順の末尾に1文** | 下記 |
| つまずき・失敗 | **ある。手順の中にわざと組み込む** | 下記 |
| 前提の棚卸し | **弱い** | 「対象読者」と「目次」はあるが、事前に用意すべきものは必要になった時点で初めて出る |

### 成功判定の書き方

> `git version`とターミナルに入力してバージョンが表示されれば完了です。
> —— Git図解

画面の見た目を言葉にする例も多い。
「logディレクトリが薄くグレーアウトしています」の直後に
「これはgitの管理から外れていることを意味しています」と**意味を足す2段構え**。

### つまずきの組み込み方（この人の一番の武器）

**「ハマった話」を書くのではなく、手順の中にわざと失敗を作る。**

**(a) 読者の心の声を代弁して割り込む**

> ここで疑問が湧いた人もいるかもしれません
> —— Docker入門

この次の行に、太字で読者のセリフを置く（「hello-worldのコンテナがdocker psで表示されない！！」）。
そして3段落で回収する。

**(b) 一度やらせてから気づかせる**

秘密情報のファイルを実際にpushさせたあとで、こう転換する。

> しかし気づきます。
> —— Git図解

そこから `.gitignore` に進む。同じ構造をもう一度別のファイルで繰り返す。
一度pushしたものは完全に消せないという落とし穴も、この流れの中で回収する。

**説明の順序が、書き手の都合ではなく読者が詰まる順に並んでいる。**

## 図58枚は何をしているのか（図が使えない場合の代替）

Git編は本文9,953字に58枚。**172字ごとに1枚。** 3種類に分かれる。

| 種類 | 枚数 | 役割 | 文字で代替できるか |
|---|---|---|---|
| 概念図 | 約24枚 | 中央集中型と分散型、ステージングの流れ、ブランチの分岐 | **難しい** |
| 操作先の画面キャプチャ | 約14枚 | 「右上の『New』をクリック」の場所を示す | **できる**（位置の言葉を添えている） |
| 結果のスクリーンショット | 約20枚 | 動いた証拠 | **できる**（直後に必ず1文の説明がある） |

### 概念図がいちばん強い場所：1文 → 図 → 1文 → 図を7回

「5. Gitワークフロー」で、これを7回繰り返している。

- **各文が新しい要素を1つだけ足す**
- **図はその1つが増えた後の全体像を毎回描き直す**

つまり**文が「なぜそれが欲しいか」を、図が「足した後の全体の形」を担当**している。

**図がない場合の代替**：7枚の積み上げは、2,000字では枠が足りない。
図1枚ずつを文に置き換えるのではなく、
**一度だけ全体の流れを1文で言い、以降は要素名だけを繰り返す。**

## タイトルと冒頭の型

タイトルは**網羅の宣言＋読者の状態**。

```
Dockerがわからない人へ。これ1本で0から学べる丁寧なDocker入門
└ 読者の状態        └ 網羅の宣言      └ 丁寧さ

【図解解説】これ1本でGitをマスターできるチュートリアル！【完全版】
```

母集団では「丁寧に・やさしく・図解」型のLGTM中央値は444、
「完全版・決定版」型は495。どちらも全体の125の3.5倍以上（→ `method/01`）。

冒頭は**自分の被害報告から始まる**。

> **私のエンジニアとしての初仕事はDockerでした。辛かったのをいまでも思い出します**
> —— Docker入門

1行目が太字の自分語りで、**書き手を「乗り越えた先輩」に位置づける。**

Git編は既存教材への宣戦布告から入る。

> 私が思う世の中にあるGitの教材のイケてない点は2つです。
> —— Git図解

そして**その2点の中身は本文になく、画像に描かれている。**

リード文の役割は「読み終えた状態」の提示。赤字太字で1文だけ置く。

## ひろほのブログに移せるもの

1. **手順の途中に読者のセリフを1行だけ太字で挟み、その場で3行以内で答える。**
   「ここで疑問が湧いた人もいるかもしれません」→ 太字でセリフ → 3行で回収
2. **正しい手順の前に、わざと1回まずい状態を作る。**
   「しかし気づきます」で転換して直すところまでを1本の流れにする。
   ひろほの「課題 → つまずき → 実例」を、物語として連結できる
3. **図の代わりに「画面に何が見えていればOKか」を1文で書き、次の1文で「それが何を意味するか」を足す。**
   見た目＋意味の2文セット。これが成功判定になる

## 移せないもの

1. **172字ごとに図を1枚差し込んで概念を積み上げる方式。**
   写真なし・2,000字では、図の代わりに全体像を言い直す文量が確保できない
2. **コマンドを打たせて出力を貼るハンズオン全体。**
   この人の「成功判定」「オプションの逐語訳」は、
   **コードブロックがあることが前提**。コードなしの条件と正面衝突する
