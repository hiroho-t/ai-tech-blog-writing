# 2,000字の型

12人の分析から、**startwith.org の `/blog` に当てられるものだけ**を1枚に落としたもの。
条件は「本文2,000字くらい・写真なし・コードブロックなし・言葉だけ・一人称は私」。

書く前にこのページを読む。書いたあとは各章のチェックリストで数える。

---

## 1. 型の全体

| # | H2 | 字数 | 何をする面か | 手本 |
|---|---|---|---|---|
| — | リード | 100〜200字 | 症状で囲い込む＋いつ時点の話か | sesere・uhyo |
| 1 | 課題 | 250字 | 読者の今の作業を箇条書き3行で言い当てる | minorun365 |
| 2 | 思い込み | 250字 | **以前の私は逆をやっていた**を直接話法で | kojimadev・luvmini511 |
| 3 | 手順 | **450字** | 番号付きで4〜5手。1手＝1動作 | minorun365・morizyun |
| 4 | つまずき | 250字 | **消費時間の実数**つきで2〜3か所 | sesere |
| 5 | 実例 | **400字** | Before／Afterを同じ行数で並べ、実数で締める | minorun365・catnose99 |
| 6 | まとめ | 200字 | 着手点を1つに絞る。同じことを2回言う | sesere |
| 7 | FAQ | 200字 | 読者が次に聞くことを3つ | — |

**合計2,000字。1見出しあたり286字**（rana_kualu 138字と morizyun 261字のあいだ。成立する → `patterns/03`）。

## 2. コードが使えない分を、何で埋めるか

技術ブログの人気ライターは、コードブロックと図に多くの仕事をさせている。
**2,000字・写真なしで同じ役目を果たすものが、3つある。**

| コード・図がしていたこと | 代わりに置くもの | 手本 |
|---|---|---|
| **成果物**（そのまま貼れるCLAUDE.md 64行） | **そのまま貼れるプロンプト全文**を引用ブロックで置く | sesere・MinoDriven |
| **成功判定**（実行結果のスクショ） | **「画面に何が見えていればOKか」1文＋「それが何を意味するか」1文** | Sicut_study |
| **操作先の特定**（画面キャプチャ） | **位置の言葉**（「右上の」「左メニューの」）を必ず添える | Sicut_study |

### 引用ブロックを成果物の置き場にする（MinoDriven 型）

コードブロックが使えない代わりに、**引用ブロックで2層構造を作れる。**

```
地の文    ＝ なぜその言い方にするかの解説
引用ブロック ＝ Claude Code に実際に打つ指示文／お客様に実際に言う台詞
```

MinoDriven は「下記のように引用で表現しますので、注意して読み進めて下さい。」と宣言してから、
引用56行を台本として渡している。**これが2,000字の記事の「真ん中に座る成果物」になる。**

### 概念図は代替できない。だから諦める

Sicut_study の「1文 → 図 → 1文 → 図」を7回積む方式は、2,000字では枠が足りない。

**代替は「一度だけ全体の流れを1文で言い、以降は要素名だけを繰り返す」。**
図1枚ずつを文に置き換えようとすると、それだけで2,000字を使い切る。

## 3. 1文・1段落の作り方

| 指標 | 目標 | 根拠 |
|---|---|---|
| 1文の平均 | **30〜40字** | 34本の中央40字。morizyun 26字・rana_kualu 32字・luvmini511 37字が読みやすい側 |
| 80字超えの文 | **7%以下** | 34本の中央7%。morizyun 1%・luvmini511 2% |
| 1段落 | **1〜2文**（40〜55字） | sesere は1段落1文・句点なし・改行で切る |
| H3 | **0本** | 2,000字でH3を作ると1本130字になる |
| 太字 | **3〜5か所**。すべて段落の最後の1文 | hirokidaichi 型（3か所） |

**※ ひろほのブログの決まりでは「1段落3〜4文」（`ai-site-writing-blog` の `articles/04_本文.md`）。**
技術ブログ側は1〜2文が主流だが、**ブログの決まりを優先する。**
ただし**手順とつまずきのパートだけは1〜2文に寄せる。** そこは読み飛ばされる前提の面だから。

## 4. 各パートに当てる型

### リード（100〜200字）

```
① 症状で囲い込む1〜2文（読者を名指ししない）
② この記事は◯◯を初めて△△する人向けです（連載の枠を作る。morizyun型）
③ いつ時点の話か（日付・バージョン）＋そのうち変わる可能性（uhyo型）
```

**効能を並べない。答えを予告しない。**（→ `patterns/04`）

### 1. 課題（250字）

読者の今の作業を**箇条書き3行**で言い当てる。
最後に1文で「その時間を何に使えるか」を置く。

### 2. 思い込み（250字）

**kojimadev の型：当時の自分の言い分を直接話法で3行書く。**

```
思い込み｜以前の私は、◯◯には△△が要ると思っていた
 「◯◯だから手作業でいいと思っていた」  ← 直接話法
 そう思っていた理由（過去の失敗）
 だから今回うまくいったときに驚いた
```

**luvmini511 の型を足すなら、〈よく見る言い方〉と〈現場でやっていること〉の食い違いを1文で。**

### 3. 手順（450字）

```
・番号付きで4〜5手（minorun365 の4ステップ固定）
・1手＝1動作。1行に2つ入れない
・各行の主語を「誰が何をするか」で書く
・画面上の位置の言葉を必ず添える（「右上の」「左メニューの」）
・どのファイル・どの画面かを毎回名指し（morizyun型）
```

**手順の直後に「こうなればOK」を1文置く。** これが7割以上の手順に付いているか数える。

### 4. つまずき（250字）

```
・2〜3か所。それぞれ「どこで・何が起きて・何分かかったか」
・消費時間の実数を必ず入れる（sesere型）
・つまずき → 教訓の2段で閉じる（minorun365型）
```

**「2026年◯月◯日時点ではできない」を1つ入れる。**（morizyun 型。記事が古くなっても嘘にならない）

### 5. 実例（400字）

```
・Before手順4行／After手順4行を、同じ行数で上下に並べる（minorun365型）
・実数で締める：時間・金額・回数のうち2種類以上
・やめたものがあれば「最初はAでやった → こういう理由でBに変えた → 前後の数字」（catnose99型）
```

### 6. まとめ（200字）

```
・着手点を1つに絞る（「まずGA4に自分でユーザーを追加できるかを、今日確かめてください」）
・その1つを、本文の中盤でも1回言っておく（sesere型：同じ1アクションを2回置く）
```

### 7. FAQ（200字）

読者が次に聞くことを3つ。**できないこと・お金のこと・危ないことを先に書く。**

## 5. 見出しの言葉づかい

現状の「課題｜月末の数字集めで、本業が止まっていませんか？」＝ラベル＋疑問文。**これは強い型。**

**7本のうち1〜2本を「業務名＋結果」に替えると変化が出る。**

| 現状 | 替えた例 |
|---|---|
| 実例｜実際につないで、何が変わった？ | **実例｜月末の数字集めが、30分から5分になった** |

**体言止めだけの見出し（「Claude Codeの設定ファイル」）は使わない。**

---

## 6. むずかしい語の扱い

```
1. 述語 → 名前 の語順で定義を1文（「Googleで何番目に出ているかを確かめる仕組みを、Googleサーチコンソールと呼びます。」）
2. 「〜とみなすと分かりやすいと思います」で日常語の見立てを1文
3. 以降は正式名だけで通す
```

**型1で定義するのは1本の記事で2〜3語まで。** 脇役の語は括弧で1語だけ足す。
比喩は1〜2個で、**必ず現物に戻す1文を足す。**（→ `patterns/02`）

## 7. 一人称

| 項目 | 基準 |
|---|---|
| 回数 | **5〜10回**（2,000字。14回が上限） |
| そのうち「私の案件では〜なので」の形 | **半分以上** |
| 自分の実力に帰属させている文 | **0個** |

**「私」は自分語りのためではなく、記事の適用範囲を絞るために使う。**（→ `patterns/05`）

## 8. タイトル

| 項目 | 基準 |
|---|---|
| 文字数 | **25〜43字**（33字が目安） |
| 「してみた」「やってみた」 | **入れない**（理由は評価の数字ではなく、検索語と一致しないため → `patterns/04` の3章） |
| 読み終わったあとの状態 | **入れる** |

**連載にするなら morizyun 型。**

```
〈ツール名〉を初めて使う人向けの〈成果物名〉
```

ツール名だけ替えて2本目が書ける。1本目に日付つきで2本目への誘導を後から差し込む。

## 9. 公開前に数える12項目

`tools/measure.py` では測れないものも含む。**目で数える。**

| # | 項目 | 基準 | 測り方 |
|---|---|---|---|
| 1 | 本文字数 ÷ H2の本数 | 250〜450字 | 目次を数える |
| 2 | 1文の平均 | 30〜40字 | `measure.py` の `avg_sent` |
| 3 | 80字超えの文 | 7%以下 | `measure.py` の `over80` |
| 4 | 日付・バージョン・「〜時点」 | 3以上 | `measure.py` の `env` |
| 5 | 「こうなればOK」を書いた手順 ÷ 全手順 | 7割以上 | 目で数える |
| 6 | 成功判定に実数が入っているもの | 1つ以上 | 目で数える |
| 7 | つまずきに消費時間を添えたもの | 1つ以上 | 目で数える |
| 8 | 「◯年◯月時点ではできない」 | 1つ以上 | 目で数える |
| 9 | 一人称 | 5〜10回 | `measure.py` の `firstp` |
| 10 | 太字 | 3〜5か所・すべて段落の最後 | `measure.py` の `bold` |
| 11 | 体言止めだけの見出し | 0本 | 目次を見る |
| 12 | 比喩に「現物に戻す1文」があるか | すべて | 目で数える |

### 自分の記事を測るコマンド

公開後なら、`tools/targets.tsv` に足して測れる。

```bash
python3 tools/measure.py tools/targets.tsv > tools/metrics.tsv
```

公開前の原稿は、原稿ファイルを直接測る簡易版を使う。

## 10. この型を使わない場合

**論考記事（「なぜこうなるのか」を書く記事）では、この型を当てない。**

hirokidaichi・uhyo が示しているように、論考では
環境・手順・成功判定・つまずきのすべてが不要で、**代わりに「置いた仮定の明示」が要る。**

| 記事の種類 | 当てる型 |
|---|---|
| 手順記事（つないだ・設定した） | **このページ** |
| 実践記（半年使った・こう変えた） | このページ＋`patterns/05` を厚く |
| 論考（なぜこうなるのか） | `writers/12_hirokidaichi.md`・`writers/11_uhyo.md` |
